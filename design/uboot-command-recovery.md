# U-Boot 命令恢复

普通命令在提交终止换行前逐字节核对回显。回显失败可能留下未提交的输入行，必须先取消这条残行，才能重新发送命令。`uboot-shell/src/command.rs` 的 `UbootShell::recover_command_prompt` 负责这个恢复过程；它不负责修复串口链路的物理误码。

## 1. 恢复边界

恢复不是重新执行命令的通用兜底。`CommandPhase` 在异步挂起和取消后保留当前阶段，只有尚未提交的输入才能进入自动恢复。

### 1.1 提交前状态

`CommandPhase::Dirty` 表示可能存在残行。`recover_command_prompt` 开始时保持该状态，只有完成严格同步后才改为 `Ready`。恢复被取消、超时或失败时，下一次调用仍必须恢复，不能直接追加命令。

`CommandPhase::Uncertain` 表示换行可能已经提交或观察到了提前执行的迹象。此时 `admit_command` 拒绝自动恢复和重放；本次改动不改变这条边界，也不增加 `MAX_ATTEMPTS` 所限制的三次命令发送。

### 1.2 时间预算

`RECOVERY_TIMEOUT` 是一次恢复共享的五秒总预算，覆盖排空输入、中断发送和刷新、响应核验，以及重新中断后的尾部排空。任何内部重试都不能重新起算这五秒。

`IDLE_TIMEOUT` 是三百毫秒的接收空闲窗口。等待中断响应时，每收到一个字节可以重新等待这个空闲窗口，但始终受总预算限制；不能给整个握手额外添加五秒，也不能让持续输入饿死总超时。

## 2. 同步流程

串口经过驱动、服务端和网络队列，读到空闲只表示当前接收流暂时没有数据，不是全链路原子清空。恢复因此同时使用有界排空和中断握手，不能把任意一个旧提示符视为成功。

### 2.1 重新中断

每次发送 Ctrl-C 前，先将当前可见输入读至空闲。随后必须收到完整的 `<INTERRUPT>` 行，允许该行带已识别的提示符前缀，并且下一行必须立即出现相同提示符。

如果等待中断响应时出现接收空闲，而总预算尚未耗尽，则重新排空，再发送 Ctrl-C。这用于处理中断字符或响应丢失、损坏后只留下不完整响应的情况，不增加命令的发送次数。错误提示符、断连及其他输入输出错误仍停止恢复，不降低握手条件。

### 2.2 完成与失败

如果本次恢复发送过不止一次 Ctrl-C，握手完成后还须在同一总预算内读至空闲，再设置 `Ready`，避免多次中断的剩余响应进入后续命令的回显。只发送一次中断且成功的路径保留原有完成方式。

这仍是有限静默窗口下的同步策略，不保证任意迟到控制流都已消失。持续链路损坏可以使恢复或后续三次命令发送失败；不能通过忽略异常字节、清除高位、延长总预算或重放已提交命令掩盖这种失败。`uboot-shell/tests/command.rs` 应通过真实 `UbootShell::cmd` 验证丢失中断响应后的恢复、超时和不重放边界。
